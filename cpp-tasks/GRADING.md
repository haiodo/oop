# ФИТ НГУ, курс ООП (C++). Правила приёма

Документ общий для всех задач. Списки пунктов по каждой задаче - в конце файла самой задачи.

## 1. Два уровня сдачи

У каждой задачи два уровня. Баллов нет: есть списки пунктов, каждый пункт либо выполнен, либо нет.

**Зачёт** - задача принята. Нужно выполнить все пункты списка "Зачёт" в файле задачи
и ответить на вопросы по своему коду.

**Автомат** - дополнительный уровень. Открывается только после зачёта по той же задаче
и требует выполнения списка "Автомат". Незачтённая основная часть с реализованным
дополнительным пунктом остаётся незачтённой: сначала работает базовое решение, потом надстройки.

Промежуточных состояний нет. Пункт выполнен наполовину - значит не выполнен.

## 2. Автоматические проверки

До разговора с преподавателем задача должна проходить проверки шаблона
[oop-cpp-template](https://github.com/haiodo/oop-cpp-template). Все они запускаются
одной командой каждая, на любой из трёх платформ. Подробности и разбор,
что именно ловит каждая проверка, - в README шаблона.

```bash
cmake --preset dev       && cmake --build --preset dev       && ctest --preset dev
cmake --preset asan      && cmake --build --preset asan      && ctest --preset asan
cmake --preset tidy      && cmake --build --preset tidy
cmake --preset coverage  && cmake --build --preset coverage  && ctest --preset coverage
cmake --build --preset dev --target format-check
```

| Проверка | Что означает |
|---|---|
| `dev` | Сборка без единого предупреждения компилятора, все тесты проходят |
| `asan` | Под санитайзерами нет ошибок работы с памятью и неопределённого поведения |
| `tidy` | `clang-tidy` не нашёл проблем, включая нарушения правил именования |
| `coverage` | Покрытие кода тестами не ниже порога, указанного в задаче |
| `format-check` | Код отформатирован по `.clang-format`; чинится командой `--target format` |

Проверки не дают преимуществ: они лишь допускают задачу к сдаче. Не прошли - разговора не будет.

Windows покрывает не всё (нет поиска утечек и проверки неопределённого поведения),
поэтому полный набор гоняется в GitHub Actions на Linux. Он уже настроен в шаблоне,
включать ничего не нужно.

Если проверка кажется вам неверной - это возможно, приходите с конкретным примером.
Отключать её у себя в `CMakeLists.txt` нельзя: правки настроек проверок в вашем репозитории
означают несданную задачу.

## 3. Разговор по коду

Проходит очно, за терминалом/ноутбуком, занимает столько времени, сколько нужно.
Это основная часть приёма, а не формальность после проверки кода. 

Разрешено: cppreference, справка компилятора, ваш собственный код и ваши записи.
Запрещено: любые внешние подсказки - поиск, переписка, генераторы кода.

Из чего состоит:

1. **Объяснение своего кода.** Преподаватель выбирает произвольные фрагменты и спрашивает:
   что делает, почему сделано именно так, что сломается при изменении.
   Ответ "это стандартный подход" ответом не считается.
2. **Живая модификация.** Преподаватель даёт изменение из банка модификаций в конце файла задачи.
   Нужно реализовать, собрать без предупреждений и покрыть тестом.
   Оценивается не скорость, а то, ориентируетесь ли вы в собственном коде.
3. **Вопросы по теме.** Язык и стандартная библиотека в пределах задачи.

Не объяснили свой код или не справились с модификацией - задача не сдана,
независимо от того, насколько хорошо она написана и все ли проверки прошли.

**Время разговора вас не ограничивает.** Если пара закончилась, а разговор не завершён,
он продолжается на следующем занятии с того же места и без каких-либо потерь:
ни зачёт, ни автомат от этого не страдают. То же самое, если до вас не дошла очередь
или занятие не состоялось. Успеть - забота расписания, а не ваша.

Разумно оценивать время можно только по тому, что вы успели показать. Поэтому
на незавершённом разговоре никакое решение не принимается: ни положительное,
ни отрицательное.

## 4. Работа с git

- Отдельная ветка на задачу, Pull Request, преподаватель в ревьюерах.
- Коммиты содержательные и распределены по времени. Один коммит на две тысячи строк -
  задача возвращается без проверки: обсуждать в ней нечего.
- Каждый коммит должен собираться. Проверить свою историю можно так:
  ```bash
  git rebase --exec 'cmake --preset dev && cmake --build --preset dev' origin/main
  ```

История коммитов - основной материал, из которого выбираются фрагменты для разговора.

## 5. Отчёт

К каждому Pull Request прикладывается `REPORT.md`:

- Команды сборки и запуска - копируются и работают как есть.
- Покрытие: число и ссылка на HTML-отчёт из артефактов CI.
- Артефакты, указанные в конце файла задачи (записи, скриншоты, замеры).
- Раздел "Известные ограничения": что не реализовано и почему.
- Раздел "Что было сложно": одна-две честных строки. Это не оценивается,
  но задаёт тему для разговора.

Артефакты должны быть получены на вашей машине, и это должно быть видно:
пути, версия компилятора, размер терминала, длительность записи.

## 6. Оформление кода

Правила действуют во всех задачах. Спорить о них не нужно: имена проверяет `clang-tidy`,
форматирование делает `clang-format`, оба настроены в шаблоне.

### Имена

Ориентир - сама стандартная библиотека: `push_back`, `to_string`, `size`.
Официального стандарта оформления в C++ нет, поэтому курс следует стилю того,
что вы расширяете.

| Что | Правило | Пример |
|---|---|---|
| Классы, структуры, перечисления | `CamelCase` | `BitArray`, `WordCount`, `CSVParser` |
| Функции и методы | `lower_case` | `push_back`, `to_string`, `split_words` |
| Переменные и параметры | `lower_case` | `word_count`, `num_bits` |
| Поля класса | `lower_case_` | `size_`, `data_` |
| Константы `constexpr` | `kCamelCase` | `kWordBits` |
| Пространства имён | `lower_case` | `word_count` |
| Макросы | `UPPER_CASE` | |

**Функции с большой буквы не используются.** С большой буквы пишутся только типы.

Проверяется автоматически:

```bash
cmake --preset tidy && cmake --build --preset tidy
```

### Форматирование

Не форматируйте руками - это делает `clang-format` по файлу `.clang-format` из шаблона:

```bash
cmake --build --preset dev --target format        # переформатировать
cmake --build --preset dev --target format-check  # проверить, не меняя
```

Ключевое: открывающая фигурная скобка на **той же строке**, отступ 2 пробела,
тело `if`/`for`/`while` всегда в фигурных скобках.

```c++
// Так:
void push_back(bool bit) {
  if (bit) {
    ++count_;
  }
}
```

`format-check` входит в CI. Незаформатированный код - незачёт, но чинится одной командой.

### Комментарии

**Только латиница.** Комментарии, имена и строковые литералы в исходниках - на английском.
Кириллица в `.h`/`.cpp` ломается на чужой локали и в чужом редакторе, а собирать ваш код
будут не только на вашей машине. Это относится к коду; `README.md` и `REPORT.md`
пишите по-русски.

**Одна-две строки.** Комментарий на абзац означает, что переписать надо код, а не комментарий.

**Только там, где код сам за себя не говорит.** Комментарий нужен, чтобы объяснить
*почему*, а не *что*:

```c++
// Плохо: пересказ имени функции, никакой новой информации.
// Increments the counter by one.
void increment();

// Хорошо: объясняет неочевидное решение.
// Bits above size_ must stay zero: count() and operator== read whole words.
void trim_high_bits();
```

Не нужны: комментарий над каждым полем, разделители вида `//////`, `// end of if`,
пересказ сигнатуры, закомментированный код (его удаляют, а не хранят).

**Публичный интерфейс документируется** в стиле Doxygen, тоже по-английски: что делает,
что принимает, что возвращает, какие исключения бросает. Здесь допустимо больше двух строк:
это документация, а не комментарий по ходу кода.

## 7. Ответственность за код

**Вы отвечаете за каждую строку в своём Pull Request.** Это главное правило курса,
остальное из него следует.

Цель курса - научиться писать и понимать код, а не получить работающий репозиторий.
Готовые решения, чужие фрагменты и генераторы кода этой цели мешают: они дают результат,
за которым нет понимания. Пользоваться ими не рекомендуется, и на разговоре по коду
это видно сразу.

Не смогли объяснить фрагмент своего кода или изменить его на месте - задача не сдана.
Проверяется не то, чем вы пользовались, а то, владеете ли вы результатом.

Практическое следствие: код, который вы не понимаете, выгоднее удалить и написать проще
самому. Короткое понятное решение всегда лучше длинного и умного.

Отдельно: тесты, которые проверяют реализацию сами на себе - `EXPECT_EQ(f(x), f(x))`,
проверки без ожидаемых значений, посчитанных руками, - не считаются тестами.
Они увеличивают покрытие и не ловят ни одной ошибки.

## 8. Что бывает, если задача не сдана

Ситуации разные, последствия у них тоже разные.

**Не успели по независящим от вас причинам.** Кончилось время занятия, не дошла очередь,
занятие отменили, преподаватель не успел посмотреть. Это **не** несдача: разговор
продолжается на следующем занятии с того места, где остановились. Ни зачёт, ни автомат,
ни срок сдачи от этого не меняются, повторно проходить пройденное не нужно.
Отсчёт недели до пересдачи здесь тоже не начинается - пересдачи нет, есть продолжение.

**Не смогли объяснить свой код или не справились с модификацией.**
Задача не сдана. Пересдача не раньше чем через неделю, автомат по этой задаче недоступен.
Нарушением это не считается: не разобраться с первого раза - обычное дело.
Разберитесь и приходите снова.

**Не смогли объяснить второй раз по той же задаче.**
Пересдача с изменёнными требованиями, которые выдаёт преподаватель. Автомат недоступен
до конца курса - по всем задачам, а не только по этой.

**Код взят у другого человека.** Признаки: совпадение с репозиторием другого студента
или с публичным решением, чужая история коммитов, чужое авторство в git.
Это единственная ситуация, которая считается нарушением.
Задача аннулируется целиком и делается заново с нуля, с другими требованиями.
Автомат недоступен до конца курса. Последствия одинаковы для обеих сторон:
кто дал списать и кто взял, отвечают одинаково.

Происхождение кода курс не устанавливает: доказать его в общем случае нельзя.
Проверяется владение кодом, а не его авторство. Не владеете своим решением - не сдали,
и этого достаточно. Нарушением считается только то, что доказуемо: совпадение
с работой другого человека.

## 9. Сроки

Сдача после дедлайна: зачёт ставится, автомат по этой задаче недоступен.

Дедлайн считается по дате Pull Request, а не по дате разговора. Если работа была готова
вовремя, а очередь на разговор дошла позже, автомат сохраняется: время преподавателя
и расписание занятий - не ваша зона ответственности.
