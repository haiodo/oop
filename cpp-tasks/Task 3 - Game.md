# Задача 3. Terminal-Based Game

Напишите небольшую terminal-based игру, то есть такую, которая использует возможности терминала (консоли) вместо графической системы. На выбор предлагаются следующие жанры и примеры (но вы ими не ограничены):

1. Фиксированный шутер наподобие [Space Invaders](https://ru.wikipedia.org/wiki/Space_Invaders).
2. Скролл-шутер (вертикальный или горизонтальный), пример: [Gradius](https://ru.wikipedia.org/wiki/Gradius).
3. Лабиринт, пример: [Pac-Man](https://ru.wikipedia.org/wiki/Pac-Man), [Bomberman](<https://ru.wikipedia.org/wiki/Bomberman_(%D0%B8%D0%B3%D1%80%D0%B0,_1983)>), ["Танчики"](https://ru.wikipedia.org/wiki/Battle_City).
4. Игра на живом поле: поле - это [игра "Жизнь" Конвея](https://ru.wikipedia.org/wiki/%D0%98%D0%B3%D1%80%D0%B0_%C2%AB%D0%96%D0%B8%D0%B7%D0%BD%D1%8C%C2%BB),
   которое эволюционирует само по себе, а игрок ездит по нему и собирает живые клетки.
   Колонии разрастаются, враги охотятся на игрока, от них можно отстреливаться.
   Вариант хорош тем, что мир действительно живёт без действий игрока - требование 2
   выполняется само собой, а не имитацией.
5. Ваш вариант.

Игры, которые делать **нельзя**:

1. Змейка.

Вы можете реализовать любую игру, удовлетворяющую следующим условиям:

1. Есть управляемый игроком персонаж и другие объекты, с которыми он взаимодействует (враги, стены, пули, и т.д.).
2. Игра в реальном времени: даже если игрок ничего не делает, на экране что-то происходит (летят пули, двигаются враги, и т.д.).
3. Есть система подсчета очков: количество убитых врагов, собранных предметов и т.д.
4. Должно быть условие окончания игры (проигрыша и/или выигрыша), например столкновение с врагом, уменьшение здоровья до 0, сбор всех предметов на экране, и т.д.

**Технические условия:**

1. Достаточно самой схематичной "графики". Например, игрок - это один символ, враги - другой символ, пули - точки, и т.д.
2. Код игры должен быть разделен на классы, каждый из которых выполняет четко определенные задачи. Отдельные функции допускаются, но основная логика работы должна содержаться в классах.
3. Должно быть как минимум 3 различных игровых объекта (например, "игрок", "враг", "пуля").
4. Все игровые объекты должны быть собраны в одну иерархию классов с единым корнем.
5. **Важно!** Поведение игровых объектов должно быть инкапсулировано в их классах. Игровой движок должен **единообразно** работать со всеми объектами. Избегайте явных проверок на тип объекта и раздельного хранения объектов в зависимости от типа. Вместо этого разное поведение разных объектов должно реализовываться средствами ООП. Основной игровой цикл должен выглядеть примерно так:

```C++
// gameObjects имеет тип std::vector<std::unique_ptr<GameObject>>
for (auto& object : gameObjects) {
    // Поведение объекта полностью инкапсулировано в его классе.
    // В движке мы не обрабатываем объекты особенным образом.
    // Мы просто у каждого объекта вызываем некий общий метод, передав ему некий контекст.
    object->act(context);
}
```

6. **Игровой цикл не должен зависеть от скорости машины.** Скорость движения объектов задаётся
   в игровых единицах в секунду, а не "за итерацию цикла". Реализуйте фиксированный шаг обновления
   (например, 30 или 60 обновлений в секунду) поверх реального времени из `std::chrono::steady_clock`.
   Цикл вида "обновить-нарисовать-`sleep(50ms)`" не подходит: на медленной отрисовке игра замедлится.
   Ввод не должен блокировать обновление: если игрок не нажимает клавиш, мир продолжает жить.
7. **Игровая логика отделена от вывода.** Классы игровых объектов и правила игры не должны вызывать
   функции curses напрямую. Это нужно, чтобы модель игры можно было протестировать без терминала.

### Два практических совета

**Не делайте объектом то, чего много.** Если в вашей игре есть фон из сотен мелких
сущностей (клетки поля, звёзды, трава), они не должны быть `GameObject`. Иерархия
и виртуальные вызовы нужны там, где поведение разное; для однородного массива данных
это только расход памяти и времени. Держите такой фон отдельной структурой данных,
а игровыми объектами делайте то, у чего есть собственное поведение.

**Согласуйте скорость с частотой обновления.** Если объект за один шаг смещается
больше чем на клетку, он может "перепрыгнуть" препятствие или цель: проверка
столкновений увидит его до и после, но не между. Либо ограничьте скорость одной
клеткой за шаг, либо проверяйте столкновения вдоль пути. Первое проще, и это
допустимое упрощение - но назовите его явно в `REPORT.md`.

### Два подвоха, на которых эта задача обычно ломается

**Почему `unique_ptr`, а не `std::vector<GameObject>`.** Полиморфные объекты нельзя хранить
в контейнере по значению: `std::vector<GameObject>` хранит объекты **точного** типа `GameObject`,
и попытка положить туда `Enemy` приведёт к срезке (object slicing) - от объекта останется только
базовая часть, виртуальный вызов уйдёт в базовый класс. Хранить надо указатели на базовый класс.
Отсюда же:

- у `GameObject` обязан быть **виртуальный деструктор** (иначе удаление через `GameObject*` - UB);
- копирование `GameObject` по значению в коде движка не должно встречаться нигде.

**Мутация контейнера во время обхода.** Пули появляются и исчезают внутри `act()`. Добавление в
`gameObjects` прямо из цикла инвалидирует итераторы - будет UB, который проявляется не сразу
и не на каждом запуске. Определите и реализуйте один из корректных вариантов, а выбор опишите
в `REPORT.md`:

- складывать новые объекты в отдельный буфер и вливать его после цикла;
- помечать удаляемые объекты флагом и вычищать одним проходом `std::erase_if` после цикла.

Стандартных возможностей С++ недостаточно для гибкого управления терминалом.
Библиотека curses уже подключена в шаблоне курса: пометьте задачу как `CURSES`,
и всё соберётся само на всех трёх платформах (ncurses на Linux и macOS, PDCurses на Windows):

```cmake
oop_task(NAME task3 SOURCES world.cpp harvester.cpp ... MAIN main.cpp TESTS game_test.cpp CURSES)
```

В шаблоне есть пример `tasks/example_terminal/` - букварь по curses: инициализация,
цвета, неблокирующий ввод, фиксированный шаг обновления, корректное завершение
через RAII. Прочитайте `README.md` рядом с ним: там разобраны типичные ошибки
устройства игрового цикла, включая ту, за которую задача не принимается.

**Это именно пример, а не заготовка.** В нём нет ни иерархии классов, ни игровых
объектов, ни отделения логики от отрисовки - всего того, что составляет суть задачи 3.
Копировать его целиком бессмысленно; взять оттуда стоит устройство цикла и RAII-обёртку.

Установка библиотеки, если понадобится: Ubuntu `sudo apt install libncurses-dev`,
macOS `brew install ncurses`, Windows - скачается автоматически.

## Альтернативный UI

Если у вас есть желание и уверенность в себе, вместо консольного интерфейса можете сделать графический. "Графика" при этом может быть такой же схематичной - прямоугольники, круги и т.д. Вариант с графическим UI будет сложнее, поэтому правильно рассчитайте свои силы.

## Приём задачи

Общие правила - в [GRADING.md](GRADING.md).

### Автоматические проверки

```bash
cmake --preset dev  && cmake --build --preset dev  && ctest --preset dev
cmake --preset asan && cmake --build --preset asan && ctest --preset asan
cmake --preset tidy && cmake --build --preset tidy
```

Под санитайзерами нужно не только прогнать тесты, но и **сыграть партию до конца**:
именно так ловится главная ошибка этой задачи - удаление объекта из контейнера
во время обхода этого же контейнера.

Порога покрытия нет, но игровая логика должна тестироваться без терминала.

### Зачёт

Первый пункт проверяется не чтением кода, а игрой. Преподаватель берёт клавиатуру
и играет; остальные пункты смотрятся уже после этого.

- [ ] **В игру можно играть.** Управление отзывчивое и предсказуемое, на экране
      понятно, где стены и куда можно двигаться, объекты различимы между собой.
      Собранная из правильных частей, но неиграбельная программа - незачёт:
      наличие класса в коде и наличие его в игре это разные вещи.
- [ ] Не менее трёх типов игровых объектов, управляемый игрок, подсчёт очков,
      условие окончания игры. Каждый тип действительно создаётся во время игры,
      а не только существует в исходниках.
- [ ] Все объекты в одной иерархии с общим корнем; у корня виртуальный деструктор.
- [ ] Объекты хранятся по указателю (`std::unique_ptr`), голых `new`/`delete` в коде нет.
- [ ] Игра идёт в реальном времени: без действий игрока на экране что-то происходит.
- [ ] Скорость не зависит от машины и от частоты отрисовки: фиксированный шаг
      от `std::chrono::steady_clock`.
- [ ] Ввод не блокирует обновление мира.
- [ ] В движке **нет** проверок типа объекта: ни `dynamic_cast`, ни `enum` с `switch`,
      ни методов вида `isEnemy()`, ни раздельных контейнеров под каждый тип.
- [ ] Создание и удаление объектов не ломает обход контейнера; выбранное решение
      описано в `REPORT.md`.
- [ ] Игровая логика отделена от вывода: классы объектов не вызывают curses напрямую.
- [ ] Есть тесты на GoogleTest без терминала: столкновение, начисление очков,
      условие конца игры, перемещение за N тактов.
- [ ] Приложена запись геймплея (см. артефакты).

### Автомат

Дополнительно к зачёту, не менее трёх пунктов из списка:

- [ ] Таблица рекордов с сохранением между запусками и просмотром из игры.
- [ ] Сохранение и загрузка игры.
- [ ] Продвинутая графика: псевдографика, объекты из нескольких символов.
- [ ] Анимация.
- [ ] Заметно более сложное поведение врагов (преследование, обход препятствий,
      разные роли), а не случайное движение.
- [ ] Звук или музыка.
- [ ] Графический интерфейс вместо терминального.
- [ ] Своя идея, согласованная с преподавателем.

### Разговор: живая модификация

Одна на выбор преподавателя. При правильной архитектуре это новый класс
и **ноль правок в движке**. Если пришлось править игровой цикл или обработку
столкновений - требование единообразия не выполнено, и зачёт не ставится.

1. Стена, отражающая пули обратно в стрелявшего.
2. Бонус: при подборе на 10 секунд удваивает начисляемые очки.
3. Враг с другим поведением движения, например преследующий игрока.
4. Пуля с ограниченным временем жизни, исчезающая сама.
5. Второй игрок на той же клавиатуре с отдельным счётом.
6. Очки за врага зависят от расстояния до игрока в момент попадания.
7. Пауза по клавише: мир замирает, после снятия паузы время не "догоняет".

### Артефакты в REPORT.md

- Запись геймплея не короче 60 секунд: `asciinema rec` для терминала, видео или GIF
  для графической версии. Должно быть видно движение объектов без действий игрока,
  начисление очков и конец игры.
- Схема иерархии классов, не больше экрана.
- Выбранное решение по изменению контейнера объектов во время обхода.
- Сколько обновлений в секунду делает игра и чем это ограничено.
