# Классы в C++

**Семинар 3**
Курс: Объектно-ориентированное программирование
2 курс

---

## Что такое класс?

- Класс - пользовательский тип данных: объединяет поля (данные)
  и методы (функции)
- Основа объектно-ориентированного программирования
- Позволяет создавать объекты этого типа

```cpp
class Rectangle {
private:
  double width_;
  double height_;

public:
  void set_dimensions(double w, double h);
  double area() const;
};
```

Геттер называется `area()`, а не `get_area()` - так называет свои методы
сама стандартная библиотека (`size()`, `empty()`, `begin()`).

---

## Объявление класса

`class` по умолчанию делает члены `private`, `struct` - `public`.
В остальном это одно и то же.

```cpp
class ClassName {
private:
  int private_field_;

public:
  void public_method();

protected:
  int protected_field_;
};
```

---

## Спецификаторы доступа

- **private** - доступ только внутри класса
- **public** - доступ из любого места программы
- **protected** - доступ внутри класса и его наследников

```cpp
class Example {
private:
  int secret_ = 0;  // Accessible only inside the class
protected:
  int family_ = 0;  // Accessible in the class and its derived classes
public:
  int value() const { return secret_; }
};
```

Публичных полей у класса быть не должно: они ломают инвариант, который класс
обязан поддерживать. `clang-tidy` сообщает об этом отдельно.

---

## Откуда подчёркивание в конце

Поле и метод с одним именем в одном классе не компилируются. Как только
появляется геттер `size()`, поле уже не может называться `size`:

```cpp
class BitArray {
public:
  int size() const;   // how many bits are stored
  int count() const;  // how many of them are ones

private:
  int size_;          // without the suffix this is a redeclaration error
  std::vector<std::uint64_t> data_;
};
```

- Подчёркивание в **конце**, а не в начале. Имена вида `_Id` и `__id`
  зарезервированы за реализацией - это формально UB и практически конфликт
  с внутренними именами стандартной библиотеки.
- Правило распространяется на приватные и защищённые поля. Публичные поля
  структур-данных (`struct World { int ball_x; };`) пишутся без суффикса:
  геттеров у них нет, конфликтовать не с чем.
- Курс следует Google C++ Style Guide - он же задан в `.clang-format`
  шаблона строкой `BasedOnStyle: Google`. Альтернатива `m_size` не хуже,
  но два стиля в одном репозитории не смешивают.

## Конструкторы

```cpp
class Point {
private:
  int x_;
  int y_;

public:
  Point() : x_(0), y_(0) {}
  Point(int x, int y) : x_(x), y_(y) {}
  Point(const Point& other) : x_(other.x_), y_(other.y_) {}
};
```

Копирующий конструктор - один из пяти специальных функций класса.
Подробно про все пять - дальше на этом семинаре.

## Список инициализации: почему не присваивание

```cpp
class Bad {
  std::string name_;

public:
  Bad(const std::string& name) {
    name_ = name;  // ПЛОХО: сначала пустая строка, потом присваивание
  }
};

class Good {
  std::string name_;

public:
  Good(const std::string& name) : name_(name) {}
};
```

`Bad` сначала конструирует `name_` по умолчанию (пустая строка), потом
присваивает значение - две операции вместо одной. Список инициализации
конструирует поле сразу нужным значением. Для полей-ссылок, `const`-полей
и полей без конструктора по умолчанию присваивание в теле вообще
не скомпилируется - только список.

---

## Ловушка: порядок инициализации

```cpp
// ПЛОХО: список инициализации не совпадает с порядком объявления полей.
class Trap {
  int b_;
  int a_;

public:
  Trap(int a) : a_(a), b_(a_) {}  // b_ инициализируется первым, читает
                                    // ещё не готовый a_
};
```

Порядок инициализации полей определяется порядком их **объявления**
в классе, а не порядком в списке инициализации. Компилятор предупреждает
об этом флагом `-Wreorder` (входит в `-Wall`) - пишите список в том же
порядке, что и поля.

```cpp
class Fixed {
  int a_;
  int b_;

public:
  Fixed(int a) : a_(a), b_(a_) {}  // list order == declaration order
};
```

## explicit: зачем нужен

```cpp
class Distance {
public:
  Distance(double meters) : meters_(meters) {}  // ПЛОХО: неявное double -> Distance

  double meters() const {
    return meters_;
  }

private:
  double meters_;
};

void print(Distance d);

void demo() {
  print(5.0);  // 5.0 незаметно стало Distance - опечатка компилируется
}
```

Конструктор, вызываемый одним аргументом, определяет неявное преобразование.
Компилятор молча подставляет его везде, где ожидается `Distance`,
не спрашивая, было ли это задумано.

---

## explicit: правило и Задача 2

```cpp
class Distance {
public:
  explicit Distance(double meters) : meters_(meters) {}

  double meters() const {
    return meters_;
  }

private:
  double meters_;
};

void print(Distance d);

void demo() {
  // print(5.0);           // Теперь ошибка компиляции.
  print(Distance(5.0));    // Намерение видно явно.
}
```

Правило: конструктор, который можно вызвать одним аргументом (в том числе
из-за значений по умолчанию у остальных), должен быть `explicit`.
Задача 2: `explicit BitArray(int num_bits, unsigned long value = 0);` -
у `value` есть значение по умолчанию, значит конструктор вызывается одним
`num_bits`, и `BitArray x = 5;` не должно компилироваться неявно.

## Методы класса: инициализация по умолчанию

```cpp
class Calculator {
private:
  double result_ = 0.0;  // NSDMI: значение по умолчанию прямо в объявлении

public:
  void add(double value) {
    result_ += value;
  }

  double result() const {
    return result_;
  }

  void reset() {
    result_ = 0.0;
  }
};
```

Без `= 0.0` поле `result_` не инициализировано, а `add()` сразу делает
`result_ += value` - чтение неинициализированной памяти, UB. Приём
называется **NSDMI** (non-static data member initializer, C++11):
работает в каждом конструкторе, где поле не переопределено в списке.

---

## Неинициализированные поля и санитайзеры

- Неинициализированное поле, которое тут же читается, - неопределённое
  поведение: компилятор не обязан ни падать, ни давать предсказуемый мусор.
- Пресет `asan` шаблона курса (`cmake --preset asan`) собирает код
  с AddressSanitizer и UndefinedBehaviorSanitizer - именно они находят
  такие чтения в рантайме, но только на пути, который реально исполнил тест.
- MemorySanitizer (MSan) ловит то же самое отдельным инструментом; в этот
  шаблон он не встроен, но знать о его существовании полезно.
- Самый дешёвый способ не наступить на это - вообще не оставлять поле
  неинициализированным: NSDMI в объявлении или явная инициализация
  в каждом списке конструктора.

## const-корректность

```cpp
class Rectangle {
public:
  Rectangle(double w, double h) : width_(w), height_(h) {}

  double area() const {                       // Не меняет объект - const.
    return width_ * height_;
  }

  void set_dimensions(double w, double h) {   // Меняет объект - не const.
    width_ = w;
    height_ = h;
  }

private:
  double width_;
  double height_;
};

void print_area(const Rectangle& r) {
  std::cout << r.area() << std::endl;  // OK: area() - const
  // r.set_dimensions(1, 1);           // Ошибка: r - const
}
```

---

## const-корректность: правила

- Метод, не меняющий состояние объекта, обязан быть помечен `const`.
- `const`-объект (и ссылка/указатель на `const`) может вызывать только
  `const`-методы.
- `mutable` снимает запрет `const` для одного конкретного поля (кэш,
  счётчик обращений, мьютекс) - используется редко и осознанно:
  `mutable int cache_hits_ = 0;`

## Деструктор и ручное управление памятью: ПЛОХО

```cpp
// ПЛОХО: свой буфер, но нет копирующего конструктора и присваивания.
class IntBuffer {
public:
  explicit IntBuffer(int size) : data_(new int[size]), size_(size) {}

  ~IntBuffer() {
    delete[] data_;
  }

private:
  int* data_;
  int size_;
};
```

Класс не объявил копирующий конструктор и присваивание - компилятор
сгенерировал их сам, побайтно (`data_` копируется как указатель,
а не как массив). Копия и оригинал начинают владеть одним и тем же буфером.

---

## Что происходит при копировании

```cpp
void demo() {
  IntBuffer a(3);
  IntBuffer b = a;  // Копирующий конструктор копирует указатель, не буфер.
}  // ПЛОХО: и a, и b вызывают delete[] на одном и том же указателе.
```

`a` и `b` владеют одним `data_`. При выходе из области видимости
деструктор отрабатывает дважды для одного буфера - double free,
неопределённое поведение. Пресет `asan` находит это мгновенно:
`heap-use-after-free` или `attempting double-free`.

## Rule of three / rule of five

Пять специальных функций класса:

1. Деструктор
2. Копирующий конструктор
3. Копирующее присваивание
4. Перемещающий конструктор
5. Перемещающее присваивание

Компилятор генерирует все пять сам - но стоит объявить руками хотя бы
одну (как `~IntBuffer()` выше), и "просто скопировать поля" в остальных
перестаёт быть безопасным по умолчанию.

- **Rule of three** (C++98): объявили деструктор, копирующий конструктор
  или копирующее присваивание - продумайте все три вместе.
- **Rule of five** (C++11): то же самое про все пять; перемещающие
  конструктор и присваивание - тема семинара 5.

Правило простое: понадобилась одна из пяти - думайте про все пять,
а не только про ту, что сломалась в тесте.

---

## Rule of three: копирующий конструктор и присваивание

```cpp
class IntBuffer {
public:
  IntBuffer(const IntBuffer& other)
      : data_(new int[other.size_]), size_(other.size_) {
    for (int i = 0; i < size_; ++i) {
      data_[i] = other.data_[i];
    }
  }
  IntBuffer& operator=(const IntBuffer& other) {
    if (this == &other) {
      return *this;
    }
    int* new_data = new int[other.size_];
    for (int i = 0; i < other.size_; ++i) {
      new_data[i] = other.data_[i];
    }
    delete[] data_;
    data_ = new_data;
    size_ = other.size_;
    return *this;
  }
private:
  int* data_;
  int size_;
};
```

Конструктор и деструктор - без изменений, см. слайд про `IntBuffer` выше.
`operator=` сначала выделяет новый буфер и только потом освобождает
старый: если `new` бросит исключение, `*this` останется нетронутым.

## Rule of zero: тот же класс через std::vector

```cpp
class IntBuffer {
public:
  explicit IntBuffer(int size) : data_(size) {}

private:
  std::vector<int> data_;
  // Нет своего деструктора и копирования: все три сгенерированы
  // компилятором и корректны, потому что std::vector сам их поддерживает.
};
```

Тот же внешний контракт, но ни одной специальной функции, написанной
руками. Rule of zero - это цель: не владеть ресурсом напрямую, а поручить
владение типу, который это уже умеет (`std::vector`, `std::string`,
`std::unique_ptr` - семинар 5). Меньше кода - меньше места для ошибки,
поэтому rule of zero предпочтительнее ручного rule of three.

## Инварианты класса

- **Инвариант** - условие, истинное для объекта между вызовами публичных
  методов (внутри метода оно может временно нарушаться).
- Инвариант поддерживают **после** каждой операции, которая могла его
  нарушить, а не чинят "по требованию" в момент чтения - иначе каждый
  метод чтения обязан помнить о починке, и рано или поздно кто-то забудет.
- Задача 2: `BitArray` хранит биты словами (`std::vector<word_t>`).
  Последнее слово почти всегда заполнено частично - неиспользуемые
  старшие биты обязаны быть нулями **всегда**.
- Нарушенный инвариант не виден в момент, когда его нарушили: `count()`
  посчитает лишние единицы, `operator==` сравнит слова целиком и увидит
  разницу там, где её по `size()` нет. Проверьте отдельно `operator~`,
  уменьшающий `resize` и `push_back`.
- Это худший вид бага: воспроизводится не там и не тогда, где сломано.

## Статические поля: определение вне класса

```cpp
class Counter {
private:
  static int count_;   // Одна копия на все объекты класса.
  int id_;

public:
  Counter() : id_(++count_) {}

  static int count() {  // Не имеет this, видит только static-члены.
    return count_;
  }
};

int Counter::count_ = 0;   // Определение обязательно вне класса.
```

---

## inline static (C++17)

```cpp
class Counter {
private:
  inline static int count_ = 0;  // Определение прямо здесь, C++17.
  int id_;

public:
  Counter() : id_(++count_) {}

  static int count() {
    return count_;
  }
};
```

`inline static` позволяет обойтись без строки определения вне класса -
поле объявлено и определено одновременно.

## Знаковые и беззнаковые типы

```cpp
// ПЛОХО: data[index] неявно приводит index к size_t, знак не проверен.
int demo_bad(int index, const std::vector<int>& data) {
  return data[index];
}
```

`std::vector<int>::operator[]` принимает `size_t`. `data[index]` - это
`data.operator[](static_cast<std::size_t>(index))`, и это приведение
компилятор с `-Wsign-conversion` обязан пометить предупреждением. Если
`index` отрицательный, приведение превращает его в огромное положительное
число - выход далеко за границы вектора вместо ожидаемой ошибки.

```cpp
int demo_good(int index, const std::vector<int>& data) {
  if (index < 0 || static_cast<std::size_t>(index) >= data.size()) {
    throw std::out_of_range("index");
  }
  return data[static_cast<std::size_t>(index)];
}
```

Задача 2 держит `int` в публичном интерфейсе и `size_t` внутри
(`std::vector<word_t>`). Каждое место, где `int` превращается в `size_t`,
обязано сначала проверить знак, иначе сборка с `-Wsign-conversion`
не проходит.

## Перегрузка операторов: какие бывают

- Арифметические: `+`, `-`, `*`, `/`, `%` и составные `+=`, `-=`, ...
- Сравнения: `==`, `!=`, `<`, `<=`, `>`, `>=` (или один `operator<=>`
  в C++20 - через два слайда)
- Индексирование и вызов: `operator[]`, `operator()`
- Унарные: `-`, `!`, `~` (например, инверсия всех бит)
- `operator&&`, `operator||`, `operator,` формально перегружаются, но
  теряют сокращённое вычисление и гарантированный порядок операндов -
  не перегружайте их

Задача 2: `&=`, `|=`, `^=`, `<<=`, `>>=` как методы; свободные `&`, `|`,
`^`, `==`, `!=`; унарный `~`; `operator[]` только для чтения.

---

## Перегрузка операторов: метод или свободная функция

```cpp
class BitArray {
public:
  BitArray& operator&=(const BitArray& other);  // Метод: меняет *this.
};

bool operator==(const BitArray& a, const BitArray& b);  // Свободная: симметрична.
```

- Составные операторы (`+=`, `&=`, ...) естественно быть методами - они
  меняют `*this`, левый операнд обязан быть объектом класса.
- `operator==` и другие сравнения - хороший кандидат на свободную
  функцию: `a == b` и `b == a` должны означать одно и то же, и не должно
  быть разницы, у какого операнда "есть метод", а у какого нет.
- Не перегружайте оператор с неожиданной семантикой (`operator+` для
  конкатенации путей вместо сложения) - читатель ожидает смысл
  из математики или стандартной библиотеки.

## Дружественные функции

```cpp
class Box {
public:
  Box(double w, double h) : width_(w), height_(h) {}

  friend double area(const Box& box);   // Часть интерфейса Box.

private:
  double width_;
  double height_;
};

double area(const Box& box) {
  return box.width_ * box.height_;   // Доступ к приватным полям.
}
```

`friend` не "взламывает" инкапсуляцию - это часть публичного интерфейса,
которую сам класс явно разрешил. Решение принимает автор класса, а не
вызывающий код. Типичное применение - свободные бинарные операторы,
которым нужен доступ к приватным полям обоих операндов.

## operator[] и прокси-классы

```cpp
class Sample {
public:
  int operator[](std::size_t i) const {  // Только чтение.
    return data_[i];
  }

  int& operator[](std::size_t i) {       // Чтение и запись через ссылку.
    return data_[i];
  }

private:
  std::vector<int> data_;
};
```

Неконстантный `operator[]` обычно возвращает ссылку на элемент. Для
битового массива это не работает: отдельного бита не существует, есть
только бит внутри слова - взять на него ссылку нельзя. `std::vector<bool>`
решает это прокси-классом - типом-обёрткой, который притворяется ссылкой
на бит (и известен ловушкой `auto x = v[0];` - `x` получает не `bool`,
а сам прокси). Задача 2 запрещает такое решение явно: неконстантного
`operator[]` в интерфейсе нет, для записи есть `set(n, val)`.

## C++20: operator<=> и = default

```cpp
#include <compare>

class Point {
public:
  Point(int x, int y) : x_(x), y_(y) {}

  bool operator==(const Point& other) const = default;
  auto operator<=>(const Point& other) const = default;

private:
  int x_;
  int y_;
};
```

`operator<=>` (spaceship) генерирует `<`, `<=`, `>`, `>=` из одного
определения. `= default` сравнивает поля класса по порядку объявления -
для `Point` это то же самое, что `x_ == other.x_ && y_ == other.y_`
вручную. Подходит, когда "сравнить все поля по порядку" - это ровно
нужная семантика. В Задаче 2 `operator==` задан как свободная функция
с конкретной семантикой (совпадение размеров и всех бит) - под такую
форму `<=>` не подставить, но идею стоит знать.

class Student {

    grades_.push_back(grade);
  }

  void print_info() const;

  std::string name_;
  int age_;
  std::vector<int> grades_;

## Пример: класс Student - реализация

```cpp
double Student::average_grade() const {
  if (grades_.empty()) {
    return 0.0;
  }
  int sum = 0;
  for (int grade : grades_) {
    sum += grade;
  }
  return static_cast<double>(sum) / grades_.size();
}

void Student::print_info() const {
  std::cout << "Student: " << name_ << ", age: " << age_
            << ", average grade: " << average_grade() << std::endl;
}
```

Методы объявлены в классе и определены отдельно - так же будет устроен
`bit_array.h` / `bit_array.cpp` в Задаче 2.

## Типичные ошибки

- Конструктор с одним обязательным параметром без `explicit` -
  `BitArray x = 5;` компилируется там, где не должно.
- Присваивание полей в теле конструктора вместо списка инициализации -
  лишняя работа, а для ссылок и `const`-полей вообще не скомпилируется.
- Список инициализации написан не в порядке объявления полей - компилятор
  предупреждает `-Wreorder`, но об этом легко забыть перед сдачей.
- Метод, не меняющий объект, не помечен `const` - откажется вызываться
  у `const BitArray&`, а именно так объект чаще всего и передают.
- Инвариант не восстановлен после операции (например, уменьшающий `resize`
  не обнулил старшие биты последнего слова) - `count()` и `operator==`
  начинают врать, баг всплывает не там, где сломан.
- Неявное приведение `int` к `size_t` без проверки знака - сборка
  с `-Wsign-conversion` не проходит.
